# SPEC: Корпоративный тариф (corp)

> Статус: черновик на ревью. Дата: 2026-11-11.
> Родительская спека: `SPEC.md`. Реализация - внутри minishop-форка `shop/` (backend) и `cabinet/` (ЛК).

---

## 1. Цель

B2B-тариф: компания покупает пакет VPN-доступов для сотрудников. Один платящий админ управляет группой: приглашает/удаляет сотрудников, включает и выключает им доступ, задаёт каждому суточную квоту трафика.

- Базовый пакет: **2300 ₽/мес = 1 админ + 10 сотрудников** (11 VPN-доступов, ~209 ₽/место - дешевле розницы 179 ₽ нет, но это пакет с управлением).
- Дополнительное место: **+200 ₽/мес** за каждого сотрудника сверх 10.
- Квота: суточный лимит ГБ на каждого участника, устанавливает админ группы.
- Месячного лимита у корп-мест нет - только суточная квота.

---

## 2. Принятые решения

| Вопрос | Решение |
|---|---|
| Кто платит | Админ группы одним платежом за все места (ЮKassa, как обычная подписка) |
| Место админа | Платное, админ сам пользуется VPN; входит в базовый пакет |
| Управление | Раздел в кабинете (Nuxt, `app.`). Бот - только уведомления и приём инвайтов |
| Онбординг сотрудников | Три способа: скопировать инвайт-ссылку (диплинк в бота), приглашение по @username, отправка ссылки на e-mail |
| Слоты | Переиспользуемые: удалил сотрудника - слот освободился под нового |
| Удаление доп-слота | Доп.слот (11+ сотрудник) можно удалить - со следующего продления -200 ₽/мес |
| Квота | Общая ставка на группу (дефолт) + персональная на каждого участника (включая админа), ГБ/сутки |
| Мониторинг | Админ видит по каждому участнику: расход сегодня против квоты, в сети ли сейчас, последнее подключение, расход за всё время |
| Лимиты | Только суточная квота; месячного потолка и переноса остатка нет |
| Минимум | 10 сотрудников - биллинговый минимум пакета, не снимаемый |
| Выключение доступа | Мгновенно, обратимо; не освобождает слот |
| Число админов | Ровно 1 на группу; передача прав - через поддержку (v1) |

## 3. Термины и модель

- **Группа (corp_group)** - организация. Один период оплаты на всю группу, единая дата окончания `period_end`.
- **Админ** - владелец группы, оплачивает её. Тоже VPN-участник (занимает админ-место).
- **Слот (seat)** - оплаченное место сотрудника. Бывает `base` (входят в пакет, всегда 10, цена не меняется) и `extra` (+200 ₽/мес, можно докупить и удалить). Слот либо свободен, либо занят участником.
- **Участник (member)** - юзер minishop, привязанный к занятому слоту или к админ-месту. Подписка участника управляется группой: `expire = period_end`, `traffic_limit_strategy = DAY`, `traffic_limit_bytes = квота`.

### Схема данных (новые таблицы в PG minishop)

```
corp_groups
  id, admin_user_id -> users.id, name (nullable),
  status: active | expired | disabled,
  period_end timestamptz, created_at

corp_seats
  id, group_id -> corp_groups.id,
  kind: admin | base | extra,
  status: occupied | free | pending_removal,
  member_user_id -> users.id (null = свободен),
  daily_quota_gb int (null = дефолт группы),
  access_disabled bool,
  occupied_at, removed_at

corp_invites
  id, group_id, token, created_by (admin_user_id),
  kind: link | username | email,
  target_username (для kind=username),
  target_email (для kind=email),
  status: pending | accepted | revoked | expired,
  expires_at, accepted_by_user_id, created_at, sent_at
```

Дефолт квоты на группу - поле `corp_groups.default_daily_quota_gb` (напр. 5 ГБ). Персональное значение на слоте перекрывает дефолт.

### Инварианты

- Свободных слотов может быть сколько угодно; занятых - не больше купленных (10 base + N extra + 1 admin).
- У участника группы ровно одна подписка, и она корпоративная. Покупки розничных тарифов для участников заблокированы (экран-заглушка "доступ предоставлен организацией").
- Юзер может состоять максимум в одной группе и не может быть админом одной и участником другой.

## 4. Механики

### 4.1 Покупка и продление

- Покупка пакета = чекаут тарифа `corp` (запись в `tariffs.json`: `billing_model: period`, `prices_rub: {"30": 2300}`, только 30-дневный период в v1). После успешной оплаты создаётся группа: админ-место занято покупателем, 10 свободных base-слотов, `period_end = now + 30d`.
- Продление = платёж на `2300 + 200 * active_extra_slots`. Сумма вычисляется корп-модулем, не из tariffs.json. Продлевает `period_end` всей группы (и всех участников) на 30 дней.
- Неоплата: `period_end` прошёл - подписки всех участников истекают штатно (в панели `expire` уже стоит), группа -> `expired`. Состав и слоты сохраняются: при позднем продлении участники получают доступ обратно без повторных инвайтов.
- Чек/фискализация - штатная ЮKassa-цепочка на админа.

### 4.2 Докупка и удаление доп-слотов

- Докупка extra-слота в середине периода: платёж `200 * (дней до period_end / 30)` с прорацией, округление до рубля. Слот активен сразу.
- Удаление extra-слота: слот -> `pending_removal`, занятый участник сохраняет доступ до `period_end`, затем слот исчезает и цена продления падает на 200 ₽. До `period_end` удаление можно отменить. Свободный extra-слот удаляется сразу.
- Base-слоты удалить нельзя - только освобождать.

### 4.3 Онбординг

Три способа пригласить сотрудника, все сводятся к одному механизму принятия инвайта и занятия слота:

**Скопировать ссылку (link):** админ генерирует диплинк `t.me/<bot>?start=corp_<token>` (одноразовый, TTL напр. 7 дней) и шлёт куда угодно. Сотрудник переходит -> `/start` с токеном -> если слот свободен, юзер занимает слот: создаётся/апдейтится его remnawave-юзер (expire = period_end группы, DAY + квота), ему показывают экран приветствия корп-доступа.

**По @username:** админ вводит username -> создаётся pending-инвайт, привязанный к username. Ограничение TG: бот не может писать первым, поэтому:
- если юзер уже стартовал бота - ему уходит сообщение с кнопкой "Принять";
- если нет - админу показывают готовую персональную ссылку с текстом "отправьте сотруднику"; при первом `/start` юзера с этим username инвайт активируется автоматически.

**На e-mail:** админ вводит адрес -> backend шлёт письмо с инвайт-ссылкой на join-страницу кабинета (`app.<domain>/corp/join?token=<token>`). SMTP-цепочка уже есть у gift-механики (`email_available` при `smtp_delivery_configured`). Получатель открывает ссылку -> логинится в кабинет (TG или e-mail-код, оба способа существуют) -> инвайт принимается, слот занимается. Работает и для тех, кто никогда не открывал бота.

**Занятие слота** - атомарная операция (гонка двух сотрудников на последний слот: второй получает "группа заполнена").

### 4.4 Управление участниками (кабинет, раздел "Корпоративный")

Админу (и только ему) в кабинете доступен раздел:

- Список участников: username, статус (активен / выключен / инвайт отправлен), квота ГБ/сутки, расход сегодня против квоты, онлайн/последнее подключение, расход за всё время, слот (base/extra).
- Действия над участником: выключить/включить доступ, изменить квоту, удалить (освобождает слот).
- Слоты: счётчик "занято X из Y", докупить extra-слот, удалить свободный/занятый extra-слот.
- Инвайты: создать ссылку (копирование), пригласить по username, отправить на e-mail, список активных инвайтов, отзыв.
- Настройки группы: имя, общая ставка (дефолт-квота ГБ/сутки). Изменение общей ставки применяется ко всем участникам без персональной квоты; отдельная кнопка "применить ко всем" сбрасывает персональные значения на общую.
- Биллинг: текущая цена продления (2300 + 200*extra), дата окончания, кнопка "Продлить".

### 4.5 Выключение доступа

- Тогл `access_disabled` -> panel API `POST /users/{uuid}/actions/disable` (обвязка уже есть в `panel_api_users.py`). Обратно - `/actions/enable`. Мгновенно, слот остаётся занятым, квота не тратится.
- Выключенный участник в своём кабинете видит статус "доступ отключён администратором".

### 4.6 Суточная квота

- Реализация - нативная: при занятии слота юзеру в панели ставится `traffic_limit_bytes = quota_gb * 2^30` и `traffic_limit_strategy = DAY`. Панель сама режет доступ при исчерпании и сбрасывает счётчик раз в сутки - отдельный учёт трафика не нужен.
- Админ правит квоту участника -> backend апдейтит `traffic_limit_bytes` на панели. Применяется сразу, без сброса уже потраченного за сутки.
- Общая ставка (дефолт группы): слоты без персональной квоты живут по ней; при её изменении backend пересчитывает лимит на панели всем таким участникам. Персональное значение на слоте перекрывает общее, пока его не сбросили.
- Админ - такой же участник с квотой; свою квоту правит себе сам.
- Момент суточного сброса определяется логикой панели (DAY-стратегия); зафиксировать фактическое поведение при имплементации и показать юзеру в кабинете ("обновится в 03:00 МСК" или rolling-окно).

### 4.6a Мониторинг расхода

Что реально отдаёт панель и что показываем админу по каждому участнику:

- расход за сегодня (`usedTrafficBytes` с DAY-стратегией - счётчик суточный) против квоты;
- "в сети" сейчас и последнее подключение (`onlineAt` / `lastConnectedNodeUuid`, уже синкается в `subscription.last_connected_at`);
- расход за всё время (`lifetimeUsedTrafficBytes`);
- список устройств с last_seen (штатная выдача устройств).

Ограничение: точных "минут онлайн в день" панель не считает - есть факт подключения/онлайна и объём трафика. Если понадобится скрин-тайм - отдельная задача поверх node-статистики.

### 4.7 Участник: что видит сам

- Кабинет: бейдж корп-тарифа, остаток сегодняшней квоты (прогресс), дата окончания периода группы, статус "активен/выключен админом".
- Раздел "Покупки" заменяется заглушкой: доступ управляется организацией, докупки/промокоды недоступны.
- Уведомления в боте: приглашение принято, доступ выключен/включён, квота изменена, удалён из группы, группа продлена/истекла.

### 4.8 Удаление участника и уход из группы

- Админ удаляет участника: panel `disable` + слот -> `free`, подписка юзера в панели обрезается (expire = now). Юзер может купить розничный тариф как обычно.
- Самовыход участника из группы в v1 - нет (только через админа). Открытый вопрос.

## 5. Затронутые компоненты

| Модуль | Ответственность | Зависит от |
|---|---|---|
| corp-core | Таблицы групп/слотов/инвайтов, DAL, доменные инварианты | - |
| corp-billing | Чекаут пакета, продление с динамической суммой, прорация extra-слотов | corp-core |
| corp-invites | Диплинк-токены, username-инвайты, занятие слота, провижининг в панель | corp-core |
| corp-quota | Установка DAY-квоты и enable/disable через panel API | corp-core |
| corp-admin-api | Webapp API роуты раздела (только для group admin) | все выше |
| corp-cabinet-ui | Раздел "Корпоративный" в `cabinet/` + карточка участника | corp-admin-api |
| corp-bot | Приём `/start corp_<token>`, DM-уведомления участникам и админу | corp-invites |

Порядок сборки: corp-core -> corp-quota + corp-invites -> corp-billing -> corp-admin-api -> corp-cabinet-ui -> corp-bot (уведомления параллельно).

### Что переиспользуется, что новое

- **Переиспользуем:** panel API (enable/disable, trafficLimit*, DAY-стратегия), чекаут/ЮKassa-цепочку, диплинк-механику `start_flow.py` (по образцу `giveaway_<id>`), карточки/экраны бота, BFF-паттерн кабинета, таблицу `subscription_notifications` для дедупа уведомлений.
- **Не переиспользуем:** gift-механику (подарок - безвозвратная передача подписки, у корп-доступа слот отзываемый и срок общий на группу); tariffs.json покрывает только чекаут базового пакета, продление и доп-места считает corp-модуль.
- **Новое:** таблицы `corp_*` (миграция chain-ом по правилам shop), сервис `corp_group_service`, webapp API роуты `/api/corp/*`, раздел в кабинете, FSM/хендлеры инвайтов в боте.

## 6. UX-кейсы и граничные случаи

- Инвайт по ссылке при заполненной группе -> "мест нет, попросите админа докупить слот".
- Админ не может удалить сам себя и не может выключить себе доступ (админ-место управляется только оплатой пакета).
- Юзер уже в другой группе -> инвайт отклоняется с пояснением.
- Админ покупает второй пакет -> запрещено, одна группа на админа (кнопка чекаута скрыта).
- Удаление слота с выключенным участником - разрешено, участник просто теряет место.
- Позднее продление после `expired`: состав восстанавливается, у панель-юзеров сдвигается `expire`.
- Смена квоты в меньшую сторону ниже уже потраченного за сутки -> участник сидит до сброса (штатное поведение панели).

## 8. Открытые вопросы

1. **Участник с активной личной подпиской**: при принятии инвайта она заменяется корпоративной без возврата (предупреждение на экране приёма) или блокируем вход до конца личной подписки? Рекомендация: заменять с предупреждением.
2. **Момент суточного сброса** у DAY-стратегии панели: полночь UTC, rolling 24ч от первого пакета или время создания юзера - проверить по факту, от этого зависит текст в кабинете.
3. **Прорация extra-слота при докупке**: предложено `200 * days_left/30`. Альтернатива - всегда полные 200 ₽ и слот живёт до конца периода (проще, но несправедливо при покупке в конце месяца).
4. **Границы квоты**: минимум 1 ГБ, максимум - ? (предложение 100 ГБ/сутки как защита от опечатки).
5. **Истёкшая группа**: сколько хранить состав и слоты без оплаты до авто-расформирования? v1 - бесконечно, чистка вручную.
6. **Нужен ли чек/счёт на юрлицо**: сейчас самозанятость - чек ЮKassa физлицу-админу. Если корп-клиентам нужны закрывающие документы - это уже ручной сценарий вне спеки.
7. **Локали/тексты**: корп-раздел добавляет десятки ключей - нужен проход по `corp_*` локалям ru/en (обязательное правило shop).
