# SPEC: Собственный VPN-сервис (Remnawave + TG-бот + Mini App)

> Статус: черновик требований. Дата: 2026-10-25, обновлено 2026-10-26 после обсуждения с Кентом (схема ranteis.app).
> Бренд: **Proliv Network**. Домен: **proliv-network.xyz** (куплен, .xyz-зона; .ru не брать - риск делегирования РКН).
> Референс UX/продукта: ranteis.eu (TG-бот + мини-апп с ЛК, рефералка, баллы).

---

## 1. Цель

Запустить собственный коммерческий VPN-сервис:

- 3 VPN-локации: **Великобритания**, **Эстония**, **Германия**
- Управление: **Remnawave** (панель + ноды, документация docs.rw)
- Продажи: **Telegram-бот** (форк 3252a8/remnawave-minishop с сильной кастомизацией) + **Telegram Mini App** (личный кабинет под собственным брендом). Архитектура: отдельный бот-сервис (TG-адаптер) + отдельный бэкенд ЛК, покрывающий всю доменную логику (платежи, юзеры, подписки, remnawave-синк, рефералка, промокоды) - кабинет и бот работают через него. В minishop это мапится на процессы backend (API+вебхуки, может работать в web-only режиме) + bot (TG) + worker.
- Доступ к нодам: **1 нода за Yandex Cloud CDN** (whitelist-профиль: RU-доступные edge-адреса Яндекса под мобильные белые списки), остальные 2 ноды - прямой доступ по VLESS+Reality
- Тариф: **179 ₽/мес**, 3 устройства, 300 ГБ трафика в месяц с переносом остатка; докупка трафика и устройств за деньги
- Триала по умолчанию нет - пробный доступ только по промокоду/рефералке

## 3. Архитектура

```
[Юзер в TG-боте]
    |
    v
[TG-бот: сервис bot из форка minishop] --API--> [Бэкенд ЛК: сервис backend] --API--> [Remnawave Panel]
    |                (VPS-0: панель, sub-page, бот, лендинг, мониторинг)
    v
[Mini App ЛК (webapp)] <----> [Subscription page sub.<domain>]
                                        | ноды подключаются к панели по ключам
   юзерские конфиги (все 3 в одной подписке):
        |                  |                  |
   uk.<domain>        ee.<domain>        de.<domain>
   A -> node UK       CNAME -> YC CDN   A -> node DE
   (VLESS+Reality)         |            (VLESS+Reality)
                     [YC CDN EE]  origin = ee-src.<domain>
                          |
        v                  v                  v
   [Node UK (VPS)]   [Node EE (VPS)]   [Node DE (VPS)]
```

### Компоненты

1. **VPS x3 ноды**: UK + EE + DE. Минимум: 1 vCPU / 1-2 GB RAM / 20 GB SSD / >=10-20 TB трафика или безлимит.
2. **VPS-0 панель** (отдельный дешёвый VPS): remnawave panel, subscription page, TG-бот, лендинг, uptime kuma. Домены `panel.<domain>`, `sub.<domain>`, `app.<domain>` - HTTPS Let's Encrypt.
3. **Remnawave nodes**: на каждой из 3 нод, привязка к панели по секретному ключу.
4. **Домен**: один - `proliv-network.xyz`, поддомены под всё:
   - `panel.` - панель
   - `sub.` - subscription page
   - `app.` - mini app
   - `wp.` - TG-прокси
   - `ee.` - CNAME на YC CDN-ресурс (whitelist-точка входа юзеров)
   - `uk.` / `de.` - A-записи прямо на VPS нод (direct-точки входа, Reality)
   - `ee-src.` - A-запись на VPS EE (origin для CDN, в конфиги юзерам не попадает)
5. **TG-бот**: продажи, тарифы, рефералка, баланс, уведомления, промокоды.
6. **Mini App**: ЛК - трафик, устройства (HWID-лимит 5), кнопка подключения, докупка.
7. **Yandex Cloud CDN**: один CDN-ресурс на EE-ноду - путь под мобильные белые списки. UK/DE ходят напрямую (Reality).
8. **TG-прокси** (веб-прокси для Telegram): `wp.<domain>`, выдача юзерам через бота. Живёт на VPS-0 или на ноде.

## 6. Yandex Cloud CDN - путь под белые списки (1 нода)

YC CDN стоит только перед EE-нодой: конфиг `ee.<domain>` - whitelist-профиль, CDN-адреса Яндекса доступны из РФ и под мобильными ограничениями. UK/DE работают напрямую по VLESS+Reality - дешевле: весь юзерский трафик через CDN - это платный исходящий трафик CDN, поэтому гнать всех юзеров через него невыгодно.

### 6.1 Проверить перед реализацией

YC CDN штатно кэширует статику; проксирование WebSocket/VPN-трафика - нестандартное применение. Тарификация (проверено 2026-10-26): **не бесплатно** - минимум 150 ₽/мес за CDN-ресурс, в платёж включены 150 ГБ исходящего трафика и 100 млн запросов; сверх объёма - pay-per-GB. Проверить:

- [ ] Поддерживает ли YC CDN проксирование WebSocket (Upgrade-заголовки) без буферизации/обрывов
- [ ] Цена за ГБ сверх 150 ГБ - прикинуть стоимость при N юзеров на CDN-профиле
- [ ] Ограничения по протоколам: CDN работает только с HTTP(S) - схема = VLESS+WS+TLS через CDN-домен
- [ ] По умолчанию на CDN заблокированы POST/PUT/PATCH/DELETE - для VLESS+WS не критично, но проверить

### 6.2 Схема

1. A-запись `ee-src.<domain>` -> IP VPS EE (origin)
2. CDN resource в YC: origin = `ee-src.<domain>`, custom domain `ee.<domain>` (CNAME -> CDN endpoint)
3. Whitelist-конфиг: connect to `ee.<domain>:443`, VLESS+WS+TLS, WS path `/ws`; CDN форвардит на origin
4. `uk.<domain>` / `de.<domain>` - A-записи прямо на ноды, VLESS+Reality
5. Все три конфига - в одной подписке. CDN-профиль можно пометить 'резерв' в имени, чтобы юзеры не гнали через него весь трафик (перебор по ГБ платный)

### 6.3 Заглушка (self-steal)

- На CDN-ноде xray WS-инбаунд с fallback: обычный HTTPS-GET на origin уходит на локальный сайт-заглушку (та же сборка лендинга) - чтобы по `ee.<domain>` в браузере открывался правдоподобный сайт
- На direct-нодах Reality сам подменяет ответ чужим TLS-сайтом (dest) - отдельная заглушка не нужна
- Корневой домен и `www` - лендинг через Caddy на VPS-0

### 6.4 Риски и план Б

- Если YC CDN рвёт WS / не пропускает - план Б: Cloudflare free (grey->orange) перед EE-нодой, либо EE тоже уходит в direct-Reality
- Если белые списки ужесточатся и CDN-адреса Яндекса попадут под блок - contingency: RU-бридж VPS (VK/YC cloud) с L4-релеем на ноды (см. бэклог)
- Рост трафика через CDN: перебор по ГБ платный - следить за счётом Яндекса; при необходимости UK/DE тоже можно завернуть за CDN добавлением ресурсов (сабы уже зарезервированы)
- Блокировка IP direct-ноды: смена IP у хостера (sevhost - 300 ₽ через тикет) или пересоздание VPS + правка A-записи uk./de.; юзерские конфиги на доменах - не трогаем

Хардкод-эмодзи в Python (приоритеты тикетов, статусы синка) тоже конвертируются - новый код должен либо использовать `<tg-emoji>` теги, либо рассчитывать на автоконвертацию; «голый» юникод в сообщениях = баг
- [x] Навигация 'одно сообщение-карточка': `/start` шлёт фото-карточку, дальше экраны меняют caption/кнопки того же сообщения (`edit_caption`); fallback на текст при отсутствии баннера или caption > 1000 символов
- Баннеры наверху карточек: лого + слоган, под каждый раздел свой - сейчас один общий `welcome.png`

## 8. Mini App (личный кабинет)

Свой webapp под бренд, открывается из бота. Хостинг: `app.<domain>` на VPS-0.

### Требования

- Авторизация: `initData` Telegram WebApp -> верификация подписи на бэкенде -> маппинг на юзера remnawave
- Экраны:
  - Главная: статус подписки, трафик (прогресс-бар), дни до конца
  - Подключение: кнопки под iOS/Android/Windows/macOS, QR-код, копирование ссылки
  - Устройства: список HWID, отвязка
  - Тарифы: покупка/продление/докупка
  - Рефералка: ссылка, статистика, вывод
- Бренд: название/лого в стиле ranteis (своё, не копировать)
- Стек (предложение): React/Vue + Telegram UI components, бэкенд = API бота или BFF к remnawave API
- [x] Админ-панель minishop на отдельном origin: `admin.<domain>` -> `remnawave-minishop-backend:8081` (Caddyfile). Наш Nuxt-кабинет на `app.<domain>` не знает `/admin/*` маршруты, поэтому бот строит админские ссылки («Открыть тикет» `/admin/support/<id>`, карточка юзера `/admin/users/<id>`) через `WEBAPP_ADMIN_URL`; при пустом значении фолбэк на `SUBSCRIPTION_MINI_APP_URL` (апстрим-поведение)

### MVP vs полная версия

- MVP: штатная subscription page remnawave как mini app (быстро, 0 разработки)
- Полная: свой webapp - отдельный этап после запуска продаж

- [ ] Секреты в .env, не в git; разные секреты на ноду/панель/бота

- [ ] Логи нод: без персональных данных, ротация
- [ ] План на блокировку IP: процедура смены IP VPS / пересоздания VPS без потери конфига (ноды stateless, конфиг в панели; на CDN-ноде правится только ee-src., на direct-нодах - A-записи uk./de.; юзерские домены не меняются)
- [ ] Firewall: на CDN-ноде инбаунд только с IP YC CDN edge; direct-ноды открыты всем (Reality)

## 10. Юридика и риски

- Продажа VPN-доступа в РФ: регуляторный риск (РКН блокирует VPN-сервисы и их рекламу; штрафы за рекламу VPN). Минимум - не рекламироваться открыто в РФ-сегменте, подготовить оферту.
- Приём картой через ЮKassa - самозанятость/ИП обязательны.
- Документы в боте (ПД, оферта) - обязательны при приёме платежей и обработке ПД.
- Yandex Cloud: аккаунт РФ, тарификация по факту - следить за счётом при росте трафика.
- Заглушка-лендинг на всех публичных хостах - часть защиты от блокировки (self-steal).
